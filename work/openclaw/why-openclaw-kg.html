OpenClaw Memory Architecture

Why we chose openclaw-kg.sqlite.

QMD already gives OpenClaw strong text retrieval. The missing piece was operational memory: a reliable way to answer what is connected to what without making the model infer config relationships from prose, stale transcripts, or vibes.

Mini 1 pilot ConfigGraph v0.2.0 SQLite graph DB 809 edges Rebuildable Read-only inputs

The decision was not QMD versus ConfigGraph. It was QMD for prose, ConfigGraph for wiring.

QMD is good at finding passages. It can answer "what did we say about this?" or "where was this decision discussed?" It is the right substrate for notes, project files, daily memory, and runbooks.

openclaw-kg.sqlite is different. It is a derived graph of structured facts: agents, models, fallbacks, crons, sessions, workspaces, providers, docs, tools, and delivery targets. Those facts come from parsers, not from LLM extraction.

The problem it solves

OpenClaw has two kinds of memory failures. Text retrieval handles the first one. ConfigGraph handles the second.

Prose recall failure

The agent forgets a decision, a runbook, a client-specific rule, or a recent lesson. QMD is the right answer here because the source material is text.

  • MEMORY.md pointer lines
  • Daily memory files
  • Project files
  • KB/wiki notes

Wiring recall failure

The agent misremembers which cron uses which model, which agent owns a workspace, or whether a stale session key still exists. That should come from config/state, not from a paragraph someone wrote three weeks ago.

  • agent -> uses_model
  • cron -> runs_as
  • model -> provider
  • doc -> mentions

Why SQLite

The graph needed to be boring, local, inspectable, and cheap. SQLite is exactly that. It gives us durable structure without importing a new database service or a batchy GraphRAG pipeline.

Auditable

The DB can be inspected with ordinary sqlite3, queried by CLI, rebuilt from source, and checked with PRAGMA integrity_check.

Deterministic

Facts are parsed from openclaw.json, OpenClaw state SQLite, and known docs. The model explains the graph after retrieval. It does not author the graph.

Portable

The same extractor can run on Mini 2 and Mini 3 later. No cloud graph DB, no service dependency, no special runtime beyond Python and SQLite.

Fast enough

The Mini 1 build runs in a fraction of a second. That makes rebuild-on-demand realistic and keeps stale graph state from becoming another memory problem.

Safer by design

Credential-looking values are redacted before metadata storage. The DB is derived and disposable, so the source of truth remains the live config and state.

Small blast radius

The tool is read-only against live OpenClaw sources and writes only the derived graph DB plus its lock file.

What it gives us

The payoff is not theoretical graph magic. It is fewer wrong assumptions, faster audits, and lower token spend when agents need operational context.

Ground-truth relationships Agents, models, fallbacks, crons, workspaces, providers, docs, and sessions become explicit edges.
Smaller context bundles The model gets the relevant graph neighborhood instead of rereading broad docs or transcripts.
Stale-state detection openclaw-kg stale surfaces broken crons, missing agent dirs, and missing DB rows.
Clear trust boundaries Config facts come from parsers; prose explains why; the active model synthesizes after retrieval.

Why not GraphRAG first

GraphRAG is the wrong center of gravity for this problem. It is useful for extracting themes from large mostly-static prose corpora. OpenClaw config memory is smaller, constantly changing, and already structured.

Layer Best at Weakness Decision
QMD retrieval Finding relevant prose in memory, project docs, daily notes, and KB files. Does not know typed operational relationships unless those are written as prose. Keep it as the text memory layer.
GraphRAG Extracting themes and communities from large document sets. LLM-extracted graph facts are expensive, batchy, and too easy to make subtly wrong. Skip for the first config-memory solve.
memory-wiki Curating prose claims, relationships, contradictions, and stale knowledge. Not the source of truth for live config, models, crons, and routing. Good later as a belief/prose layer, not the config graph.
ConfigGraph Representing current OpenClaw operational wiring from parsed source of truth. Does not explain human rationale by itself; it needs QMD/project docs for that. Build first. Pair with QMD.

What it stores

The DB is not a memory diary. It is a compact operational map with provenance. Current Mini 1 sources include live config, OpenClaw state, and selected shared docs.

Nodes

  • agents, agent dirs, agent DBs
  • models, providers, model catalogs
  • cron jobs, sessions, channels
  • docs, workspaces, tools, plugins

Edges

  • uses_model, falls_back_to
  • runs_as, routes_to
  • owns_workspace, documents
  • mentions, configured_in

Issues

  • cron consecutive errors
  • main-session systemEvent crons
  • missing agent dirs
  • missing agent database rows

How it changes retrieval

The agent can now answer operational questions in two passes: first retrieve the wiring, then fetch the prose around that wiring only when needed.

Before

Search notes, skim docs, maybe inspect config manually, then rely on the model to keep relationships straight in a long context window.

Now

Ask openclaw-kg for the agent, model, cron, doc, or stale neighborhood. Pull QMD snippets only around the relevant nodes.

Result

Better answers with fewer tokens, less drift, and a cleaner audit trail back to exact files, rows, and commands.

The database is not sacred.

openclaw-kg.sqlite is derived, rebuildable, and disposable. The sacred part is the rule: operational facts come from source parsers, not model memory.

Current commands

These are the practical interfaces that make the graph useful during normal agent work.

Build or refresh

openclaw-kg build --refresh

Inspect one agent

openclaw-kg agent steipete

Inspect one model

openclaw-kg model openai/gpt-5.5

Trace a relationship

openclaw-kg trace agent forge

Find drift

openclaw-kg stale

Machine-readable output

openclaw-kg why model openai/gpt-5.5 --json
