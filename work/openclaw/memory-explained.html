OpenClaw Memory, Sea Level

The memory system is not magic. It is a disciplined filing room.

Mini 1 keeps a working memory for OpenClaw agents by saving important facts in files, building indexes over those files, checking live system state, and making the model answer from evidence instead of vibes.

The simplest version

The model does not permanently remember everything. The system writes things down, keeps a map of where they live, searches that map when a question arrives, and hands the model the relevant notes before it answers.

Five parts of the memory loop Save, index, retrieve, answer, and update.
Mini 1 OpenClaw memory system

Source files

Project docs, KB notes, daily logs, config files, and live SQLite state are the written record.

Indexes

Search tools build shortcuts so the agent can find the right note or relationship quickly.

Retrieval

When asked a question, the system pulls only the likely relevant facts into the conversation.

Answer

The active LLM reads the retrieved evidence, reconciles conflicts, and explains the current truth.

Write-back

After substantial work, the important result is written to the right project or KB file.

What "memory" means here

Human memory feels like recall. Agent memory is closer to an organized office: there are folders, indexes, labels, current-status boards, and rules about which source wins when two notes disagree.

Long-term notes

Durable facts live in project files and KB docs. That is where current URLs, runbooks, client rules, workflows, and lessons belong.

Pointer memory

MEMORY.md is not the encyclopedia. It is the table of contents that points agents to the real source documents.

Live state

For operational questions, the system checks config and databases because old notes can be stale. Current state beats old memory.

The two finders

Mini 1 uses two different retrieval styles because notes and machine configuration are different kinds of information.

QMD finds written context

QMD searches text: memory files, project docs, daily logs, and KB articles. It is good for "what did we decide?", "what happened last time?", and "where is the runbook?"

ConfigGraph finds system relationships

ConfigGraph reads live OpenClaw config and state into a map of agents, models, cron jobs, sessions, tools, docs, and delivery targets. It is good for "what is wired to what?"

Why this matters

Without a memory system, every session starts from a foggy transcript and the model has to guess what still matters. With memory, the agent can check the record.

Less drift Answers are grounded in current files and live state, not stale recollection.
Faster starts The agent can load the few relevant notes instead of rereading everything.
Better handoffs Another agent can pick up from project files rather than hidden chat history.
Auditable answers Important claims can point back to a file, command, or live config source.

A normal question

The memory system is easiest to understand by watching a simple question move through it.

"What LLM is steiPete running?"
  • The agent checks the live session status or OpenClaw config first.
  • It may use project docs or memory to explain why the route changed.
  • It answers with the current model and fallbacks.
  • If the docs are stale, the durable project file gets updated.

The trust ladder

Not every memory source deserves equal trust. The system uses a simple order of confidence.

Most trusted

Live config, live databases, current project files, and verified command output.

Useful, but derived

Indexes and graph databases. They are fast and helpful, but they can be rebuilt from source.

Useful, but cautious

Old transcripts and daily notes. They explain history, but they may not describe today.

The whole point

Memory is not a bigger prompt. It is a habit: write the important things down, store them in the right place, retrieve only what matters, check live reality, and leave the record better than you found it.
